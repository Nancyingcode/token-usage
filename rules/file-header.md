# 文件头内容规范

## 1. 目的

文件头注释用于说明文件的职责、业务边界、关键约束和维护注意事项，帮助开发人员快速理解文件用途。

文件头应尽量保持简洁，只保留长期有效的信息。

---

## 2. 推荐原则

文件头建议回答以下问题：

1. 这个文件负责什么？
2. 这个文件不负责什么？
3. 修改时有哪些约束或注意事项？
4. 是否存在相关文档、配置或依赖模块？

对于职责清晰、内容简单的文件，不强制添加文件头。

---

## 3. 推荐字段

团队可统一使用以下字段：

```ts
/**
 * @file 文件名称或核心职责
 * @description 文件的业务说明
 * @see 相关文档或模块
 */
```

字段说明：

| 字段 | 是否必需 | 说明 |
| --- | --- | --- |
| `@file` | 推荐 | 描述文件名称或核心职责 |
| `@description` | 推荐 | 描述业务用途、边界和主要功能 |
| `@see` | 可选 | 指向相关文档、模块或配置 |
| 约束说明 | 可选 | 描述修改要求、调用限制或注意事项 |

---

## 4. 不推荐字段

不建议在文件头中维护以下内容：

```ts
/**
 * @author 张三
 * @date 2026-07-23
 * @lastModified 2026-07-24
 * @copyright xxx
 */
```

原因：

- 作者信息可以通过 Git 提交记录查询。
- 创建时间和修改时间容易忘记维护。
- 多人协作后，作者字段容易产生误导。
- 修改记录应由 Git Commit、Pull Request 和 Changelog 管理。
- 重复维护信息会增加无效成本。

---

## 5. 通用模板

```ts
/**
 * @file 文件职责
 * @description
 * 描述该文件的主要功能、业务边界和使用场景。
 *
 * 约束：
 * - 约束一
 * - 约束二
 *
 * @see 相关文档或模块
 */
```

## 6. 不同文件类型示例

### 6.1 React 组件

```tsx
/**
 * @file 用户列表
 * @description
 * 展示用户数据，并提供筛选、分页和状态修改功能。
 */
```

复杂组件可以补充边界说明：

```tsx
/**
 * @file 用户列表
 * @description
 * 负责用户列表展示、筛选和分页交互。
 *
 * 不负责：
 * - 用户权限数据初始化
 * - 用户详情数据管理
 */
```

### 6.2 React Hooks

```ts
/**
 * @file usePermission
 * @description
 * 提供当前用户权限判断能力。
 */
```

### 6.3 工具函数

```ts
/**
 * @file 日期格式化工具
 * @description
 * 提供业务统一的日期解析、格式化和时区转换方法。
 */
```

### 6.4 Service 或 API 文件

```ts
/**
 * @file CMS 内容发布服务
 * @description
 * 负责内容发布、撤回及发布状态同步。
 *
 * 约束：
 * - 不直接操作页面状态
 * - 发布请求必须携带内容版本号
 * - 并发冲突由调用方统一处理
 */
```

### 6.5 配置文件

```ts
/**
 * @file CMS 菜单配置
 * @description
 * 定义菜单层级、路由映射及权限标识。
 *
 * 修改菜单时需同步检查：
 * - 路由配置
 * - 权限编码
 * - 国际化文案
 */
```

### 6.6 状态管理文件

```ts
/**
 * @file 用户状态管理
 * @description
 * 管理用户基础信息、登录状态和权限数据。
 *
 * 注意：
 * - 页面临时状态不应存放在此文件
 * - 异步请求统一由 service 层处理
 */
```

### 6.7 自动生成文件

```ts
/**
 * 此文件由脚本自动生成，请勿手动修改。
 *
 * 生成命令：pnpm generate:api
 * 数据来源：openapi.json
 */
```

自动生成文件必须明确标识，避免开发人员直接修改生成结果。

### 6.8 核心业务文件

```ts
/**
 * @file 内容差异对比
 * @description
 * 比较 CMS 内容的两个版本，并生成字段级差异结果。
 *
 * 约束：
 * - 忽略字段由 diffIgnoreFields 配置维护
 * - 富文本内容需要先完成标准化
 * - 返回结果不得包含原始敏感字段
 *
 * @see docs/content-diff.md
 */
```

## 7. 适合添加文件头的场景

建议以下文件添加文件头：

- 核心业务模块
- 复杂组件
- 公共 Hooks
- 公共工具函数
- 状态管理文件
- API 或 Service 文件
- 路由、权限、菜单等配置文件
- 自动生成文件
- 存在特殊约束的文件
- 容易被误用或误改的文件

---

## 8. 可以不添加文件头的场景

以下文件通常不需要强制添加文件头：

- 职责非常清晰的小组件
- 单一常量文件
- 简单类型声明文件
- 文件名已能准确表达用途的文件
- 内容很少且不存在特殊业务约束的文件

例如：

```ts
export const DEFAULT_PAGE_SIZE = 20;
```

这类文件增加文件头的收益较低。

## 9. 编写要求

### 9.1 描述职责，而不是重复文件名

不推荐：

```ts
/**
 * @file user-list
 * @description 用户列表文件
 */
```

推荐：

```ts
/**
 * @file 用户列表
 * @description
 * 展示用户数据，并提供筛选、分页和状态修改功能。
 */
```

### 9.2 描述原因和约束，而不是代码实现

不推荐：

```ts
/**
 * 使用 map 遍历数组，然后调用 filter 过滤数据。
 */
```

推荐：

```ts
/**
 * 过滤当前用户无权限访问的菜单项。
 *
 * 注意：
 * 父级菜单无可见子项时必须一并移除。
 */
```

### 9.3 避免维护容易过期的信息

文件头中不应记录：

- 当前负责人
- 最近修改人
- 最近修改日期
- 临时需求编号
- 已废弃的历史修改过程
- 可以从 Git 中查询的信息

### 9.4 修改代码时同步检查文件头

当文件职责、业务边界或关键约束发生变化时，应同步更新文件头。

普通代码调整、变量重命名或内部实现优化，通常不需要修改文件头。

---

## 10. 团队推荐规范

1. 不强制所有文件添加文件头。
2. 核心业务和复杂文件必须说明职责。
3. 自动生成文件必须标注“禁止手动修改”。
4. 禁止在文件头维护作者和修改日期。
5. 修改文件职责时必须同步更新文件头。
6. 文件头应控制在合理长度内，避免写成业务文档。
7. 详细设计内容应放到 `docs` 目录，并通过 `@see` 引用。
