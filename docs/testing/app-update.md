# 应用稳定版在线更新验证与发布准备

依据：[已确认设计](../superpowers/specs/2026-10-22-app-update-design.md)。离线修复、NSIS 维护页、
安装范围和安装器数据保留的完整步骤见[安装器维护隔离验收](installer-maintenance.md)。

本文记录当前实现、可重复验证方法和发布前门槛，不表示真实安装场景已通过。本轮只覆盖自动化测试、
使用合成状态的界面预览与本地未签名打包；未运行真实产品安装器、未执行发布工作流、未创建远程草稿，
也未正式发布。真实签名、双版本在线更新、UAC 和缩放验收继续暂停，待另行授权。

## 1. 支持范围与用户操作

- 首期面向 Windows x64 打包应用，只接受高于当前版本的稳定版 `major.minor.patch`，
  不支持预发布、构建元数据或降级；价格目录同步与应用更新相互独立。
- 更新源固定为公开的 `Nancyingcode/token-usage` GitHub Releases。Renderer 只能发出无 URL、
  路径或令牌参数的命令；客户端不内置 GitHub Token，不上传本地配置或会话内容。
- 设置页展示当前版本、目标版本、纯文本说明和下载进度。用户依次执行“检查更新”“下载更新”
  “重启并安装”，应用不自动检查或下载，普通关闭、退出和重启不会安装已下载更新。
- “重启并安装”调用主进程原生确认框，默认和取消选项均为“稍后”。取消后保持当前版本运行；
  只有确认才进入安装准备。
- 安装准备暂停新业务操作与后台生产任务，等待已开始的应用数据写入结束，再启动现有 NSIS。
  准备失败不启动安装器，并恢复可继续操作的状态。此过程只处理应用自己的数据；会话数据源始终只读。
- 开发模式、不支持的平台、构建时缺少 `WINDOWS_PUBLISHER_NAME` 的版本不提供在线更新。
  桌面版的“下载安装包 / 修复”按钮仍打开固定发布页；浏览器无 preload 时安全显示不可用。
- 没有 updater 的历史安装不能通过自身获得该功能。用户须先离线安装一次包含 updater、正确签名且
  配置了发布者身份的新版，作为后续在线升级的起点。

本次不改变存储 schema、产品 appId/NSIS GUID、应用数据路径或已有安装范围。更新与离线修复继续
保留应用配置和可重建缓存；未来如需变更存储格式，应单独设计迁移，不能把本次更新机制当作迁移保证。

## 2. 失败、取消与恢复边界

| 场景 | 客户端行为与恢复方式 |
| --- | --- |
| 检查失败或版本无效 | 显示可读错误，可重新检查；不会下载或安装 |
| 下载失败 | 保留已检查的目标版本，用户可以重试下载 |
| 下载完成后普通退出 | 不调用安装；之后仍需显式执行检查、下载和安装流程，缓存命中不等于授权安装 |
| 原生确认框取消 | 不进入安装准备，继续使用当前版本 |
| 安装前写入等待失败 | 显示保存失败，恢复应用操作，不启动安装器；用户可重试，仍需重新确认 |
| 启动安装器失败且应用仍运行 | 显示安装失败并恢复应用操作，可重试安装，仍需重新确认 |
| UAC 取消 | 安装尚未获授权，原安装应保持不变；应用可能已经退出，需要手动重新启动旧安装 |
| 原生安装中途失败 | 记录具体失败阶段，按隔离环境证据处理；不承诺任意阶段自动回滚或自动重启 |

UAC、进程交接和 NSIS 失败发生在应用退出边界附近，单元测试无法证明真实系统行为。
问题版本应通过更高稳定版本修复发布；需要修复当前版本时使用该版本的离线安装包，禁止通过降级绕过。

## 3. 本地检查与隔离界面预览

开发过程中运行相关最小测试集，交付前按项目门禁执行：

```powershell
npm test
npm run typecheck
npm run lint
npm run build
npm run build:win
```

`build:win` 明确传入 `--publish never`，不会上传产物或创建 Release。可使用已缓存的 Electron
二进制执行 `npm run build:win:cached`，并在执行记录中说明。没有签名证书的本地构建可用于检查
打包产物；未配置发布者时，在线功能按设计不可用，离线入口保留。未签名产物不能作为正式分发包。

自动化检查覆盖状态机、显式授权、取消和失败重试、并发及过期响应、安装前暂停和写入等待、IPC
调用来源与参数边界、中英文 UI、发布配置和草稿限制。UI 预览只注入合成快照，不连接真实 updater，
不读真实配置或会话目录，也不通过预览按钮启动安装器。应覆盖以下展示状态：

| 状态 | 检查重点 |
| --- | --- |
| 不可用 / 尚未检查 / 无更新 | 原因可读；没有自动检查或下载；可用桌面桥接保留离线入口 |
| 发现更新 | 当前与目标版本、纯文本说明、明确的下载按钮 |
| 下载中 | 真实快照驱动进度，可访问名称和状态反馈；互斥操作禁用 |
| 下载完成 | 显式“重启并安装”入口，没有倒计时或自动安装 |
| 准备 / 安装中 | 显示阶段，禁用冲突操作 |
| 失败 | 说明与阶段对应，重试入口正确，不泄露原始路径、令牌或内部错误 |

本轮已用模拟页面观察中文发现更新、英文下载进度和下载完成状态；这不构成 Windows 原生确认框、
NSIS 页面、真实 UAC 或 DPI 验收。完整安装与签名检查仍按第 5 节记录。

客户端在下载完成与每次安装前都重新计算安装包 SHA-512，并使用系统 PowerShell 验证有效签名和
精确发布者。系统工具不可用、校验报错、摘要或发布者不匹配时均拒绝安装。已对系统自带且签名有效的
PowerShell 可执行文件做只读正反验证：正确发布者通过，错误发布者和摘要均拒绝；未运行该文件作为安装器。
原生 PowerShell 首次模块加载会向 stderr 输出进度 XML，因此固定脚本关闭进度输出，仍将真实错误视为失败。

2026-10-22 本地完成记录：165 个测试文件、1060 项测试通过；typecheck、lint、完整 build 与
`build:win:cached` 通过。最终产物的版本仍为 `0.1.0`；已核对 `latest.yml` 摘要/大小、blockmap
结构/总大小与 ASAR 文件范围。安装器、应用和提权辅助程序的实际签名状态均为 `NotSigned`，
不能将 builder 输出的 signing 日志解释为已签名；本次产物仅用于本地构建检查。

## 4. 签名与仅草稿发布流程

当前流程适用于公开仓库。若未来转为私有分发，需要重新设计下载授权，不能把维护者令牌写入客户端。

### 4.1 维护者配置

| 配置 | 位置与要求 |
| --- | --- |
| `WINDOWS_PUBLISHER_NAME` | 仓库变量 `vars.WINDOWS_PUBLISHER_NAME`；与证书 SimpleName/CN 严格同名，无前后空格 |
| `CSC_LINK` | 仓库 Secret `secrets.CSC_LINK`；用于导入签名证书，建议 Base64 编码的 PFX |
| `CSC_KEY_PASSWORD` | 仓库 Secret `secrets.CSC_KEY_PASSWORD`；证书密码，不写入源码或日志 |
| `GITHUB_TOKEN` | GitHub Actions 内置凭证，工作流需要 `contents: write`；无需为客户端配置 PAT |
| `GH_TOKEN` | 只在创建草稿的 CI 步骤中赋值为内置 `secrets.GITHUB_TOKEN`，不传入客户端或签名构建步骤 |

发布构建使用 [electron-builder.release.cjs](../../electron-builder.release.cjs)，继承已有 NSIS
身份并强制代码签名与更新签名验证。缺少证书、密码或发布者时停止。初始安装与后续更新必须使用
匹配的受信任发布者身份；证书身份变更需要单独评估兼容性，不能临时关闭签名校验。

### 4.2 授权后的执行步骤

1. 在授权发布准备后，确定稳定版本和对应已有标签。标签必须为 `vX.Y.Z`，与标签所指代码中的
   `package.json` 完全一致；三个数字段不得含前导零，不接受预发布或构建元数据。
2. 手动运行 [.github/workflows/release-draft.yml](../../.github/workflows/release-draft.yml)，
   输入该标签。流程只接受 `workflow_dispatch`，普通提交、标签推送或本地构建不会触发发布。
3. 工作流检出 `refs/tags/<tag>`，验证本地标签并固定 40 位提交 SHA，使用
   [scripts/release-draft.cjs](../../scripts/release-draft.cjs) 的 `--validate` 检查版本与身份。
4. 执行签名构建，仍传入 `--publish never`，并运行测试、类型检查和 lint。
5. [scripts/release-utils.cjs](../../scripts/release-utils.cjs) 校验本次产物与签名；创建草稿前
   再核对 GitHub 上的远程标签仍指向固定提交，兼容 annotated tag。
6. 草稿脚本拒绝任何同标签已有 Release，包括草稿；不会更新、覆盖、删除或发布既有 Release。
   仅调用 `gh release create --draft --verify-tag` 创建新草稿，后续正式发布必须另行授权。

必须来自同一次构建的发布资产为：

```text
Codex-Token-Usage-Setup-<version>-x64.exe
Codex-Token-Usage-Setup-<version>-x64.exe.blockmap
latest.yml
```

校验包含 `latest.yml` 的版本、安装包路径、SHA-512 和大小，以及 blockmap 结构和总大小。
安装器、`win-unpacked/CodexTokenUsage.exe` 与 `win-unpacked/resources/elevate.exe` 必须有
有效且带时间戳的 Windows 签名，发布者精确匹配。嵌入卸载器由 builder 签名；当前草稿脚本没有
独立提取卸载器验签，因此仍须在隔离安装后补验。不能只看构建日志中的 signing 字样判断签名成功。

草稿仅供维护者检查，普通客户端不能从草稿获取更新。创建草稿不等于完成在线升级验收或正式发布；
本次没有实际执行上述工作流，也没有创建任何远程草稿。

## 5. 待授权的真实隔离验收

使用可恢复的 Windows 虚拟机、Sandbox 或独立测试用户，不以开发用户的现有安装作为目标。
只使用合成会话 fixture 和隔离测试账户的应用配置；不得复制真实日志，或访问真实用户会话目录。
记录 Windows 版本、用户类型、安装范围、语言、DPI、版本/提交、哈希、签名身份与证据位置。
跨账户 UAC 必须有标准用户及另一管理员账户，单管理员 Sandbox 不能替代。

在线端到端测试需要两个正确签名的稳定版本，基线版本已包含 updater，更新版本高于基线。
当前客户端固定公开发布源、且不会读取 draft，因此真实更新资产的可见性和发布动作必须另行授权；
不能为了测试私自发布、修改客户端源或跳过签名校验。

| 验证组 | 操作与预期结果 | 当前状态 |
| --- | --- | --- |
| 签名与身份 | 验证安装器、应用、提权辅助程序及安装后卸载器的发布者、可信状态与时间戳；无效或不匹配签名不得安装 | 待授权 |
| 历史版本引导 | 从不含 updater 的隔离历史安装手动升级到带 updater 的签名基线；确认配置与安装身份保留 | 待授权 |
| 双版本在线更新 | 基线检查到高版本，明确下载，确认后安装并重启至目标；未点击、取消确认及普通退出均不安装 | 待授权 |
| 当前用户 / 所有用户 | 两种范围分别更新，保留目录、范围、卸载登记和快捷方式偏好；不产生额外副本 | 待授权 |
| UAC 与跨账户 | 分别授权和取消，记录进程是否退出；取消时旧安装仍可启动；另一管理员账户场景无误操作其他安装 | 待授权 |
| 网络与安装失败 | 下载中断、损坏包、进程占用与安装启动失败都有对应反馈；重试仍需要用户授权 | 待授权 |
| 数据保护 | 制造未完成的测试配置写入，确认安装等待其完成；核对应用配置与 fixture 的清单、哈希和权限 | 待授权 |
| 中英文与缩放 | 100%、150%、200% 下检查更新卡片、原生确认框与 NSIS 长文案；键盘、焦点、状态播报和按钮不截断 | 待授权 |
| 离线修复 | 在线不可用或更新失败后，固定入口可获取对应版本安装器并修复；不改变会话数据源 | 待授权 |

每轮恢复快照后重测，并结合[安装器维护隔离验收](installer-maintenance.md)核对路径、范围、静默
拒绝与快捷方式。不将文件哈希未变当作“从未读取文件”的证据；若验证数据访问边界，跟踪也只针对
合成 fixture。验收记录必须分别标明通过、失败、未执行和证据，不能用自动化测试或打包成功代填。
