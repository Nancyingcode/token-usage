# Windows 安装器修复与更新设计

状态：用户已明确确认本版设计并授权开始实施。
实施依据见[实施计划](../plans/2026-10-22-installer-maintenance.md)。

## 1. 目标与现状

重新运行安装包时，明确区分首次安装、修复当前版本和更新到新版本，减少重复选择与误操作。
沿用现有 electron-builder / NSIS、中英文原生向导和 Windows x64 离线安装包。

当前依据：

- [打包配置](../../../electron-builder.yml) 已固定应用 ID、GUID、可执行文件名和安装范围选项。
- [安装器扩展](../../../build/installer.nsh) 只提供欢迎页、桌面快捷方式选择和安装后处理，没有维护页或版本比较。
- [现有设计](./2026-08-11-windows-nsis-installer-design.md) 约定原位升级、保留应用数据，未包含在线自动更新。
- [打包测试](../../../tests/packagingConfig.test.ts) 保护身份、资源及数据源边界，尚未验证修复、禁降级和维护状态。
- 当前锁定的 electron-builder / app-builder-lib 为 26.15.3；项目没有应用更新客户端和发布源配置。

## 2. electron-builder v26 NSIS 依据与取舍

查阅日期：2026-10-22。按用户指定，以
[electron-builder v26 NSIS 官方文档](https://www.electron.build/v26/docs/nsis/)为主要设计依据，
具体可用配置与执行顺序以锁文件对应的 app-builder-lib 26.15.3 类型定义和模板核对。
官网 v26 文档仍可能更新，不能把同一主版本后续新增能力当作 26.15.3 已支持的能力。

| 能力 | 26.15.3 原生边界 | 本项目方案 |
| --- | --- | --- |
| 安装向导与权限 | `oneClick: false` 提供辅助向导；安装范围和 UAC 有原生流程 | 保留首次安装体验，维护时锁定原范围 |
| 定制入口 | 官方推荐 `include` 扩展 | 在 `build/installer.nsh` 增加维护页和操作判断，复用安装主体 |
| 修复与更新菜单 | 类型定义没有修复或更新菜单开关 | 自定义同版本修复、新版本更新入口，调用原生重装管线 |
| 版本与降级 | 默认安装模板不提供本设计的版本分类和禁降级策略 | 读取本产品版本登记，执行第 3 节的项目规则 |
| Windows 修复入口 | 模板登记 `NoModify=1`、`NoRepair=1` | 维护入口为重新运行安装包，保持系统卸载入口现状 |
| 桌面快捷方式 | 默认重装行为与显式 `always` 重建不同，缺失程序时还存在模板分支差异 | 保留用户选择；修复时按明确选项恢复 |

表中模板结论来自本地 `nsisOptions.d.ts`、`assistedInstaller.nsh`、`multiUserUi.nsh`、
`installSection.nsh` 与 `include/installer.nsh`，它们位于
`node_modules/app-builder-lib/`，只作为核对依据，不修改或复制整个模板。
维护页、版本比较、禁降级、范围冲突处理和快捷方式偏好属于本项目扩展，不宣称是官方内建功能。

本期的“更新”是**使用当前下载的新版本安装包原位更新**，界面写明目标版本，离线可用。
它不代表联网检查最新版本，也不代表当前包一定是最新版本。
官方[自动更新方案](https://www.electron.build/v26/docs/features/auto-update/)由 `electron-updater`、
发布源和更新元数据共同提供；本期保留这个后续接入方向，不将 NSIS 安装包等同于更新客户端。
`nsis-web` 是联网获取安装内容的目标，`uninstallUrlUpdateInfo` 是更新说明链接，均不能替代
更新检测与安装逻辑。
本项目没有可选组件，因此不增加空的“修改组件”入口；卸载继续使用 Windows 已有卸载入口。

## 3. 维护入口与状态规则

启动时读取本产品在当前用户与所有用户范围内的安装登记。已有唯一、可识别安装时，
显示“维护 Codex Token Usage”，包含已安装版本、安装包版本、原安装位置和安装范围。
“修复当前版本”和“更新至安装包版本”同时可见，不可用项附静态原因说明。

| 检测结果 | 默认操作 | 修复项 | 更新项 |
| --- | --- | --- | --- |
| 没有本产品安装登记 | 首次安装 | 不显示维护页 | 不显示维护页 |
| 已安装版本等于包版本 | 修复当前版本 | 可用 | 禁用，提示本包与已安装版本相同 |
| 已安装版本低于包版本 | 更新至包版本 | 禁用，提示修复原版本需要对应版本安装包 | 可用，明确显示旧版本 → 新版本 |
| 已安装版本高于包版本 | 无 | 禁用 | 禁用，提示已有更高版本，请使用对应或更高版本包 |
| 版本缺失、格式不支持或登记相互矛盾 | 无 | 禁用 | 禁用，说明无法可靠识别现有安装 |
| 当前用户与所有用户各有一份安装登记 | 无 | 禁用 | 禁用，提示先通过 Windows 卸载入口处理重复安装 |

存在登记但程序 EXE、资源或卸载器丢失，不等同于首次安装；只要身份、版本、路径可可靠识别，
仍允许符合版本关系的修复或更新。登记完全丢失时不遍历磁盘寻找程序，也不猜测原版本。

维护界面示意，版本仅为示例：

```text
维护 Codex Token Usage

已安装版本：0.1.0                 安装包版本：0.2.0
安装范围：当前用户               安装位置：原安装目录

○ 修复当前版本                   [不可用]
  修复 0.1.0 需要使用 0.1.0 安装包。

● 更新至 0.2.0
  更新程序文件，保留配置和数据源设置。

                         [取消]  [更新]
```

主按钮随操作显示“安装”“修复”或“更新”，未选择有效操作时禁用。
禁用原因不用仅悬停提示或颜色表达；控件支持 Tab、方向键、空格和可访问名称。
所有标题、说明、错误、完成文案同时维护英文与简体中文 NSIS 资源。

## 4. 修复与更新的具体承诺

### 4.1 修复

- 使用同版本安装包重新部署应用管理的程序文件、卸载器和开始菜单入口。
- 修复范围是程序安装损坏，不重置主题、语言、预算、价格覆盖、缓存或数据源路径。
- 保持原安装目录、安装范围和应用身份，不提供通过修复搬迁目录或切换用户范围的选项。
- 桌面快捷方式按保存的偏好恢复；旧安装没有偏好登记时，以操作前快捷方式状态为默认值，
  并在修复页提供明确的创建选项，以便用户恢复误删的快捷方式。
- 不宣称执行逐文件哈希校验、清除所有未知残留文件或修复操作系统环境。

### 4.2 更新

- 仅当安装包版本高于已安装版本时可执行，按数值版本顺序判断，禁止旧包降级覆盖。
  该保护适用于包含本设计逻辑的新安装器，不能追溯阻止用户运行已发布且没有此保护的历史包。
- 保持原目录、范围及快捷方式选择，维护路径不再要求用户重新选择安装参数。
- 明确提示配置会保留；完成页显示实际安装的目标版本，可选择启动应用。
- 本期比较合法的稳定版 `major.minor.patch`。预发布、构建元数据或无法解析的历史版本
  不擅自截断、不按字符串比较、不当作版本零；显示不支持维护的原因并停止写入。
  后续若发布此类版本，需先扩展并测试相应版本语义。

### 4.3 权限、关闭与失败

- 首次安装保留原向导；修复和更新锁定已登记范围与目录。当前用户安装不主动提权，
  所有用户维护继续复用 NSIS 的 UAC 流程，取消授权后停止操作。
- 原生进程占用处理负责关闭提示与重试，自定义脚本不按进程名额外批量结束进程。
- 执行前校验登记路径与所选范围一致；维护模式拒绝通过 `/D` 或范围参数迁移既有安装。
- 修复和更新拒绝 `--delete-app-data` 参数，交互与静默路径均在执行旧卸载器之前停止，
  防止上游将该参数传给旧卸载器而破坏数据保留约定。
- 在进行文件替换前重新校验版本、目标和状态；UAC 内外实例须得出相同的操作决定。
- 写入前取消应保持原安装不变。写入开始后沿用原生取消和失败语义，不承诺任意阶段自动回滚。
- 安装失败不得显示成功或启动残缺应用；提供可读错误和重新运行对应安装包的处理提示。
  不新增清空配置或强制删除安装目录作为恢复手段。

## 5. 数据与安全边界

应用 ID `io.github.nancyingcode.tokenusage`、现有 NSIS GUID、`CodexTokenUsage.exe` 和
`%APPDATA%\codex-token-usage` 保持不变。修复和更新保留整个应用数据目录。

安装器只处理本产品登记、程序文件及自身管理的快捷方式，不读取应用的数据源设置来定位会话。
安装、修复、更新、卸载均不扫描、读取、修改或上传真实 Codex 会话数据源。
维护检测只查询固定产品键，不能为了查找旧安装遍历用户目录、会话目录或其他产品登记。

异常登记中的根目录、系统目录、相对路径或跨范围目标不作为替换目标；无法确认本产品归属时
停止维护，不执行递归删除、目录搬迁或泛化清理。仅有同名 EXE 不能作为应用身份凭据。

## 6. 实现约束与可行性依据

本节限定实现边界，不代替确认后的实施计划。

1. 继续使用 `build/installer.nsh` 与必要的局部 include。`customInit`、`customWelcomePage`、
   `customInstallMode` 和 `customInstall` 属于官方文档列出的扩展宏；
   `customPageAfterChangeDir`、`customFinishPage` 另经本地 26.15.3 模板确认存在，
   升级构建工具时必须复核这些模板扩展点。复用原生安装主体，不复制完整安装/卸载模板、
   不修改 `node_modules`，也不通过 `script` 切换成完整自定义安装器。
2. `customInit` 在原生安装范围初始化之后运行，可读取已选范围对应的 `InstallLocation`
   与卸载登记的 `DisplayVersion`。包版本来自构建注入的 `${VERSION}`，不另存版本真值。
3. `${isUpdated}` 代表命令行更新模式，不能用来判定“机器已经安装”或版本大小，也不能为了
   跳过页面伪造该标记。交互与静默安装共享同一版本与目标校验，不能只在页面回调中检查。
4. 原生范围选择允许改变范围，使用 `customInstallMode` 锁定维护目标。目录页按以下局部扩展
   接入：将 `allowToChangeInstallationDirectory` 设为 `false`，关闭模板自动插入的目录页；
   在 `customPageAfterChangeDir` 中插入标准 `MUI_PAGE_DIRECTORY`，用本页的 PRE 回调
   在维护状态下跳过，仅首次安装展示。已核对该扩展点位于配置条件之外、范围页之后。
   这样首次安装仍可自选目录，维护保持原路径，无需伪造 `${isUpdated}` 或替换完整模板。
   关闭自动页也会关闭原生 `instFilesPre` 的应用子目录整理，须通过局部函数保留首次安装的
   原有路径行为，并在替换前重验维护目标。它还会影响原生快捷方式保留分支，修复必须明确
   恢复开始菜单入口，更新保留既有快捷方式状态；不能只验证目录页是否隐藏。
5. 当前模板在所有用户安装时可能连带卸载当前用户副本，因此双范围登记先中止，不能承诺
   不受支持的“任选其中一份单独维护”。提权后也要保留并复核外层检测的冲突状态。
   使用另一管理员账号授权时，内层 HKCU 可能指向不同账户；须同时考虑外层调用者和内层
   账号的登记，任一存在会被连带卸载的用户副本均停止维护，不能仅复用外层无冲突结论。
6. 在原生清理旧安装前快照快捷方式状态；新增桌面快捷方式偏好只写入所维护范围的本产品
   安装登记，成功安装后保存。旧版本升级时使用已有快捷方式状态兼容，不修改应用配置格式。
7. 旧卸载器丢失时，上游流程可能继续解包；必须用隔离的真实安装包测试确认修复结果与残留
   边界，不能单凭源码推断宣称验收通过。
8. 静默同版本安装执行修复，高版本执行更新，低版本、未知版本、冲突范围与迁移参数返回非零
   结果并保留原因；不展示需要用户操作的自定义维护页，也不新增静默安装参数。
9. 本期不增加生产依赖，不改变包管理器、IPC、Renderer、主进程或用户数据持久化模型。

预期涉及安装器 include、必要的 `electron-builder.yml` 选项、安装器测试与 README。
保持现有应用 ID 和显式 GUID，不能因为官方支持根据应用 ID 自动生成 GUID 而切换既有安装身份。
没有实际必要时不修改构建脚本、锁文件和品牌图片。现有注释不随意删除。

## 7. 验证与验收

确认设计后，行为变更按红—绿—重构执行。先补充失败用例，再实现对应安装器行为。

- 自动化覆盖版本关系、`0.9.0 → 0.10.0`、不支持的版本、双范围登记、缺失文件、
  目录/范围冲突、静默模式和中英文资源一致性。
- 目录配置从原生自动页改为 include 中的标准目录页后，更新配置断言并验证首次安装仍能
  自选目录、应用子目录行为兼容、维护页跳过目录选择以及修复能恢复缺失的开始菜单入口。
- 自动化测试应验证实际使用的安装器判断路径；不得仅建立一份未被 NSIS 使用的 JavaScript
  状态逻辑来证明安装器正确。静态配置断言只保护身份和安全不变量。
- 现有 Vitest 不能完整执行 UAC、文件占用和 Windows 向导；实现前先记录可重复的隔离验证
  步骤，并使用编译后的安装包验证，不能把字符串断言视为安装流程测试。

隔离 Windows 用户、虚拟机或 Sandbox 中执行：

| 场景 | 验收结果 |
| --- | --- |
| 首次安装 | 中英文、范围、目录、快捷方式、完成启动行为保持兼容 |
| 同版本修复 | 删除测试安装的 EXE/资源/卸载器后仍可恢复，版本不变 |
| 跨版本更新 | 显示明确版本变化，目录与范围不变，仅一条对应卸载登记 |
| 旧版本包与异常版本 | 交互及静默路径均在替换前停止 |
| 桌面快捷方式 | 覆盖曾选择、曾取消、手动删除及旧版无偏好登记情况 |
| UAC、进程占用、失败 | 提权取消安全停止；换管理员账号授权仍检查冲突；占用有重试/取消；失败不显示成功 |
| 双范围与危险参数 | 不误卸载另一范围，不因 `/D` 写到其他目录；拒绝 `--delete-app-data` |
| 配置和会话 fixture | 操作前后配置内容与 fixture 哈希一致，不访问真实会话目录 |
| 回退重进与静默安装 | 状态不串联，不跳过校验；静默模式无自定义交互页 |
| 可访问性与显示 | 键盘可用、禁用原因可读，中英文及 100%/150%/200% 缩放无裁切 |

隔离验证使用独立用户数据和测试会话 fixture；数据保留断言在完成后启动应用之前采集，
避免正常启动产生的缓存写入干扰结果。不会在当前开发用户的真实安装或会话数据上做破坏测试。

实施完成后至少运行：

```powershell
npm test
npm run typecheck
npm run lint
npm run build
npm run build:win
```

必要时可以使用项目已有的 `build:win:cached` 读取本地 Electron 二进制，并说明验证方式。
记录安装器构建结果与实际执行的隔离场景；未执行的 UI/UAC 验证、正式签名状态应单独列出。

### 实施核对发现的原生边界

26.15.3 模板在 `preInit` 和 `customInit` 之前执行 `SetOutPath $INSTDIR`。
隔离最小 NSIS 夹具已确认：即使随后立即拒绝并退出，`/D` 指定的不存在目录也可能已被创建为空目录。
当前 include 无法在该语句之前执行校验，因此“拒绝迁移”可以保证不部署程序、不调用旧卸载器，
但不能宣称候选目录绝对零写入。该限制未通过删除目录、修改依赖或复制完整模板绕过；
复现证据和实际安装验收状态见[隔离验收文档](../../testing/installer-maintenance.md)。
