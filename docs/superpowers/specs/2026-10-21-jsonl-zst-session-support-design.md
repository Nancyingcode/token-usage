# JSONL Zstandard 压缩会话手动导入设计

状态：用户已确认“两份独立数据、压缩数据手动刷新、保存完整解压 JSONL”，开发与验证已完成。任务拆分及验证证据见[实施计划](../plans/2026-10-21-jsonl-zst-session-support.md)。

## 1. 用户确认的行为

- 原始 `.jsonl` 是实时数据，继续按 60 秒、窗口聚焦和普通刷新按钮更新。
- 检测到 `.jsonl.zst` 后提供独立的“刷新压缩数据”按钮，用户自行决定是否刷新。
- 只有该按钮可以触发压缩源内容读取与解压，启动和自动刷新均不触发。
- 手动刷新后，在应用本地保存**解压后的完整 `.jsonl` 文件**，保留完整内容，而非仅保存 Token 汇总或解析结果。
- 实时源文件与本地已导入文件分开维护；界面合并两份数据进行统计，同一逻辑来源只计一次。
- 原始压缩文件和整个源目录始终只读；本地解压副本由应用自己的存储目录管理。

## 2. 数据划分与刷新规则

| 数据集合 | 内容与位置 | 更新时机 | 重启后的行为 |
| --- | --- | --- | --- |
| 实时数据 | 当前选定会话目录中的普通 `.jsonl` | 启动、每 60 秒、聚焦、普通刷新按钮 | 按原扫描流程读取与复用解析缓存 |
| 已导入数据 | 应用 `userData` 下完整解压的 `.jsonl` 及来源清单 | 用户点击“刷新压缩数据”后增补或替换 | 直接加载本地副本，复用解析缓存，不重新解压源文件 |

两份数据分别维护更新时间。普通刷新完成不意味着压缩数据已检查或已更新；界面分别显示“实时数据扫描时间”和“压缩数据上次导入时间”。

自动扫描可在现有目录遍历中顺带识别 `.jsonl.zst` 文件名，以展示手动操作入口，但不对压缩文件执行内容读取、解压或指纹检查。根据文件名与本地来源清单，只能知道发现数量和从未导入的来源数量，不能声称同路径压缩文件没有更新。

已导入文件的本地解析结果在运行时驻留，60 秒周期只合并该已加载结果，不重读全部本地副本。应用重启或解析缓存失效时可以重新解析本地副本，这不属于刷新压缩源。

## 3. 用户界面

在用量页面提供独立的压缩数据提示区，不挤占原刷新按钮的含义：

- 按用户确认的紧凑状态条方案，默认显示待导入数量、本地副本数量和“刷新压缩数据”按钮；“详情”展开后显示发现数量、完整统计、两份更新时间及说明。
- 已存在本地导入数据时，即使当前源压缩文件已删除，仍显示本地文件数，并可展开查看上次导入时间。
- 用户可以不点击按钮，继续使用实时数据和已有本地副本；未导入的新压缩内容不进入统计。
- 原刷新按钮的可访问名称明确为刷新实时数据；压缩刷新按钮独立显示正在检查、导入进度、成功、部分失败或失败。
- 没有实时会话、只有压缩文件时，提示区和按钮仍可访问，不能被空数据界面遮挡。
- 重复点击压缩刷新复用同一个进行中的任务，按钮在任务期间禁用；原有数据显示和实时扫描继续可用。
- 刷新结果报告新增、更新、未变化和失败的文件数，失败项提供来源路径与不含会话原文的技术原因。
- 新增文案同时维护英文与简体中文；状态通过文本和可访问反馈传达，按钮可键盘操作。
- 当前统计范围和待导入文件未计入统计的短提示始终可见；进度、刷新结果、错误和失败文件入口放在折叠区域外。
- 状态条展开或窗口高度不足时，概览内容可以纵向滚动。趋势图保留可读的最小高度，不得为了压进首屏而缩成零高度；宽窗口继续利用剩余空间。

首版不增加自动导入开关或定时压缩刷新任务。

## 4. 本地完整文件与来源清单

建议新增 `compressed-session-store`，专门保存用户手动导入的数据。其性质是持久化数据存储，不能沿用普通解析缓存“损坏即丢弃”的处理方式。

目录示意：

```text
userData/
  imported-sessions/
    <source-root-key>/
      manifest.json
      raw/
        <immutable-version-id>.jsonl
      staging/
        <import-id>.tmp
```

- `source-root-key` 由规范化的源根目录确定，清单同时保存根目录身份以校验归属。不同数据源目录隔离；切换目录只加载对应集合，切回后可继续复用。
- 清单包含 schema 版本、源根目录、逻辑来源、原始压缩来源路径、源指纹、当前本地版本文件、解压文件大小及内容摘要、该来源导入时间。
- 每次实际解压生成新的不可变版本文件；不先覆盖已生效文件再更新清单。只有清单引用的版本参与统计，不能递归扫描 `raw` 或 `staging` 把旧版本重复计入。
- 完整副本保存原始解压字节，包括未参与 Token 计算的记录；不经过 JSON 重新序列化，也不因个别坏 JSONL 行而删改原文。
- `UsageSession.sourceFile` 保留原始 `.jsonl.zst` 来源标识，实际本地文件路径由存储层单独维护；解析时使用原始来源标识，避免内部版本文件名改变会话 ID。
- 原始压缩文件删除、移动或暂时不可读，不自动删除已经导入的本地副本。手动刷新采用增补与更新语义，不把源文件缺失解释为删除本地数据。
- 解析结果可另存为可重建缓存，按本地不可变版本和解析版本索引；完整原文及来源清单才是持久化依据。解析规则升级时可直接重新解析本地原文。
- 清单损坏、版本不支持或引用的原文缺失时，明确报告本地导入数据不可用并保留原文件，不静默置空、不覆盖成空清单，也不自动访问压缩源修复。
- 首版不自动清理已经生效或曾经生效的完整原文。只允许清理已确认属于失败任务且没有清单引用的临时文件；历史版本清理另行设计。

保存位置必须位于应用拥有的目录，并与只读源目录隔离。主进程校验清单路径与本地文件归属，拒绝路径越界；Renderer 不接收任意读写路径能力。

## 5. 手动刷新的执行流程

```text
用户点击刷新压缩数据
  → 捕获当前源目录身份，枚举并检查压缩文件指纹
  → 已导入且指纹未变：复用已有完整副本
  → 新增或变化：只读源文件，严格解压到应用 staging
  → 完整性校验、检查源文件未变、关闭输出、解析本地副本
  → 将成功文件置为不可变版本，生成候选清单
  → 原子保存清单成功
  → 切换运行时已导入集合，与最新实时集合去重汇总
  → 发布用量变更，沿现有链路更新预算与费用分析
```

### 5.1 成功与失败的边界

- 对单个来源，必须完整解压并通过完整性检查才允许提交。读取期间指纹变化、截断、校验和错误或写入失败都保留旧版本；首次导入失败则不计入该来源。
- 完整解压后的 JSONL 坏行沿用现有警告语义，原文完整保存，其余有效行仍可统计。
- 一次手动刷新可提交成功的文件，失败来源保留旧版本并显示“部分失败”；不能把部分结果描述为全部成功。
- 必须等待新版本文件和清单完成持久化后才显示导入成功。清单保存失败时不切换内存集合、不更新成功时间、不发布候选变更；旧清单和旧文件继续有效。
- 中断或重启后只读取最后完整有效的清单。完成写入但尚未被清单引用的文件不参与统计。
- 全部未变化时可更新本次检查状态，但保留“最近实际导入时间”的含义；检查时间与导入时间不混用。
- 未发生任何成功提交时不推进导入成功时间；有部分提交时记录各文件时间，并保留本次部分失败状态。

### 5.2 并发与目录切换

手动解压在候选集合中进行，实时扫描继续读取普通源文件。仅在发布阶段串行提交，使用**当时最新**的实时集合与候选导入集合合并，避免长时间解压覆盖较新的实时结果。

源目录切换与提交通过同一运行时协调；旧目录任务不得把结果发布到新目录。任务携带目录身份或世代标识，切换后停止旧任务或禁止其提交。已完成并已提交的旧目录副本保留，供以后切回使用。

## 6. 汇总、去重与统计范围

逻辑来源身份由源根目录、源目录内相对路径和去掉末尾 `.zst` 的文件名构成。仅把同目录的 `a.jsonl` 与 `a.jsonl.zst` 本地副本视作同一来源，不按 `sessionId` 全局合并不同文件。

- 同一逻辑来源同时存在于实时集合和本地导入集合时，实时 `.jsonl` 优先，合计只计一次；本地副本仍保留。
- 实时文件消失且已有本地副本时，本地副本重新参与统计，其导入时间明确保留。若本地副本比最后实时内容旧，统计反映的是已导入快照，不能声称包含尚未导入的新内容。
- 实时来源读取失败时，沿用现有失败与旧结果保留机制，不静默用较旧本地副本冒充实时读取成功。
- **原 `.jsonl` 被外部压缩后，如果该来源从未手动导入，它会退出实时集合，合计可能暂时下降。** 此时显示尚有压缩数据未导入；用户手动刷新后才恢复对应历史。首版不自动把旧普通缓存转存为第三份数据。
- 尚未导入压缩数据时，概览说明当前范围为“实时数据 + 已导入压缩数据”，不能宣称覆盖全部源数据；预算和费用分析需同步呈现该覆盖范围提示，不能将已知范围内的数额称为完整历史总额。
- 费用仍按当前定价规则重新计算，完整原文与 Token 数据不固化为某次价格；未知模型继续标记未计价。

完整用量结果和费用变更集都由**合并去重后的有效集合**生成。不能把实时扫描的删除列表直接传给成本运行时，否则会误删仍由本地副本承接的历史来源。来源从普通切换为压缩副本时，同一周期发布旧有效来源删除与新有效来源写入。

启动、目录切换、导入集合加载以及派生费用索引重建时，必须提供足够的有效来源信息；不能因为本地解析缓存命中就漏发重建所需的数据。

## 7. 解压技术与现有解析器复用

### 7.1 已验证的运行时边界

此前已对本工作区使用纯内存合成数据探测：Electron `43.4.0` 内嵌 Node `24.18.1`，开发 Node 为 `24.17.0`，都提供内建 Zstandard API；[Electron 发布信息](https://releases.electronjs.org/release/v43.4.0)与实测版本一致。

裸解压在这两个运行时中出现：同一输入 chunk 内串联两帧时只返回首帧、截断输入仍返回部分内容、首帧后的垃圾被忽略。Node 官方已有[截断输入问题记录](https://github.com/nodejs/node/issues/64592)，但不能依据问题关闭推断当前运行时已正确处理。

手动触发只能控制刷新成本，不能替代完整性检查。仍推荐“严格分帧校验 + 内建异步解压”，先通过实际 Electron 能力测试再接入业务。不新增生产依赖；根 `@types/node` 从当前锁定的 20 系列对齐 Node 24，并验证 CI 运行时。

### 7.2 严格解压与原文落盘

按照 [Zstandard 格式规范](https://github.com/facebook/zstd/blob/dev/doc/zstd_compression_format.md)处理帧头、块头、负载、最后块、可选校验和与可跳过帧，按结构分流，不通过搜索 magic bytes 切帧。

- 每个数据帧使用独立异步解压器，按顺序将解压字节写入同一临时文件，保持背压；不缓冲整份压缩文件或解压内容。
- 验证全部输入被合法帧消费；截断帧、非法尾随字节、缺少外部字典、错误 checksum 和不匹配的内容大小均不得形成生效副本。
- 允许标准单帧、串联多帧、合法可跳过帧和没有声明内容大小的帧；不支持外部字典配置和其他压缩格式。
- 零字节压缩文件失败；合法空内容帧可保存为空 JSONL，沿用现有空内容解析语义。
- 一个 UTF-8 字符或 JSONL 行可以跨帧，原样连接字节后再解析，不能逐帧解析后求和。
- 保持受控并发，首版建议 `MAX_CONCURRENT_ZSTD_IMPORTS = 2`，用合成大文件验证资源占用；失败时关闭关联源流、解压器和输出流。

### 7.3 解析范围保持局部

用户选择持久化完整原文后，首版可以直接读取已完成的本地 JSONL，并复用现有 `parseSessionJsonlAsync`，无需为本功能重写 Token 累积核心或新增流式 parser。

现有解析器仍会持有完整文本，只是分批让出事件循环；流式解压落盘不等于解析阶段常量内存。通过限制同时导入和解析的文件数控制峰值，压力测试记录大文件解析内存与界面响应。若测试表明确实需要流式 parser，再单独细化该局部改造。

仍须修正 `getSessionId` 对 `.jsonl.zst` 的支持，保证来源标识、会话 ID 和 `session_index.jsonl` 任务名称关联一致。会话索引继续使用普通文本读取，名称可在实时刷新时重新关联；不触发压缩导入。

## 8. 接入范围与持久化安全

| 模块 | 调整 |
| --- | --- |
| [usageScanner.ts](../../../src/main/usageScanner.ts) | 保留普通文件扫描，顺带发现压缩文件名；扫描结果和缓存先暂存，成功后统一提交 |
| 新增压缩导入服务与本地文件 Store | 管理手动任务、严格解压、不可变完整文件、原子清单与来源指纹 |
| [usageRuntime.ts](../../../src/main/usageRuntime.ts)、[applicationRuntime.ts](../../../src/main/applicationRuntime.ts) | 协调实时集合与本地集合，生成合并结果和变更集，隔离导入失败与普通刷新 |
| [usageMonitor.ts](../../../src/main/usageMonitor.ts) | 60 秒与聚焦调度只触发实时路径 |
| [sessionId.ts](../../../src/shared/sessionId.ts) | 支持复合后缀，维持稳定会话 ID |
| [usageScanCacheStore.ts](../../../src/main/usageScanCacheStore.ts)及本地解析缓存 | 仅作为解析加速；不可替代完整导入文件和来源清单 |
| [ipc.ts](../../../src/main/ipc.ts)、[ipcChannels.ts](../../../src/shared/ipcChannels.ts)、[preload.ts](../../../src/preload/preload.ts)、[global.d.ts](../../../src/renderer/global.d.ts) | 新增类型化压缩状态读取、手动刷新和进度订阅；主进程使用当前已验证源目录 |
| Renderer、中英文资源和相关测试 | 独立按钮、两份时间、导入状态、覆盖范围及部分失败提示 |

不能继续在扫描尚未成功时修改已提交缓存，否则失败轮中其他来源的更新可能在恢复后被当作缓存命中，漏发费用变更。普通扫描和导入发布各自使用候选状态，统一生成已成功状态的有效来源差异。

Renderer 不直接访问文件系统，也不决定导入目标路径。所有源目录操作限于遍历、读取与获取元数据；写入仅发生在应用管理且不与源目录重叠的存储区域。持久化失败必须保留旧文件，不通过删除旧版本来修复写入失败。

## 9. 验证与验收

设计确认后编写中文实施计划，包含行为代码的任务按红—绿—重构执行。所有测试使用合成数据、仓库 fixture 或独立临时目录。

1. **刷新隔离**：启动、60 秒、聚焦及普通刷新均不会读取压缩内容、解压或刷新本地副本；只识别文件名。未点击按钮时不会发生导入写入。
2. **完整保存**：手动导入后的本地文件字节与压缩前原文一致，包含非 Token 记录和坏 JSONL 行；重启及源文件删除后仍可读取本地副本。
3. **原子性**：旧版本不原位覆盖；文件写入、解析或清单保存失败不切换生效版本；崩溃遗留文件不自动参与统计；清单损坏不被当作空数据覆盖。
4. **解码能力**：开发 Node 和实际 Electron 验证单帧、多帧、不同 chunk 边界、可跳过帧、未知大小、RLE 块以及截断、尾随垃圾、checksum、字典和内容大小错误。
5. **手动增量**：未变化来源不重复解压；新增和变化来源分别增补与替换；失败保留旧副本；混合成功与失败显示部分失败；源缺失不清除本地数据。
6. **合并范围**：实时与导入副本去重，同名不同目录不误合并；实时源压缩但尚未导入时范围提示准确；来源切换、删除和费用索引结果一致。
7. **生命周期**：重复点击单飞；实时扫描与导入重叠不覆盖更新；目录切换不串数据；重启水合与派生索引重建完整；缓存失败恢复不漏发变更。
8. **界面与可访问性**：只有压缩文件时仍能操作；两份更新时间清晰；新增、未导入、部分失败与不可用状态均有中英文文案和辅助技术反馈。
9. **性能与只读**：大文件流式落盘、并发上限、解析内存与事件循环可响应；确认所有写入都在应用拥有的目录，源数据完全不变。
10. **完整门禁**：实施后执行 `npm test`、`npm run typecheck`、`npm run lint`、`npm run build`，并执行 Electron 实际运行时解压冒烟测试。
