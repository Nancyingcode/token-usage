# 条件计价：第二阶段设计

状态：用户已确认，第二阶段本地实现和验证已完成。实施记录见[实施计划](../plans/2026-09-10-conditional-pricing.md)。

## 1. 目标和边界

在第一阶段联网价格目录基础上，支持有证据的长上下文、缓存写入和运行模式计价，区分规则匹配、假设估算和未计价。费用始终是按当前价格重新计算的本地估算，不代表账户实际账单。

优先支持 Astra 的已核对规则；其他模型只有在其目录条目具有明确规则来源时才能应用倍率，禁止跨模型继承 Astra 的规则。不新增对真实会话文件的写操作，不上传日志，不接入账户账单，不根据模型名称或响应速度推测运行模式。

## 2. 已检查的事实

- 当前解析器保留五类 Token 数量，但没有保留缓存写入和请求计价条件。
- 2026-09-10 对默认会话目录最近五个文件做只读字段抽样，首次统计覆盖 168 个 token_count 事件。均存在 last_token_usage.cache_write_input_tokens；36 个 turn_context 均没有 service_tier 字段。只输出字段统计，未复制原始日志到仓库或网络。
- 后续一次动态抽样未发现正数缓存写入，也未发现缓存读取加写入超过总输入。因此字段存在已确认，但正数分区语义不能仅凭这次样本证明；实施时需核对上游协议或可信的脱敏正数 fixture。
- token_count.info.model_context_window 是模型容量，不是请求实际输入，不能用于计价阈值判断。
- 当前只有累计用量时，会将最大累计记录作为一个切片。这类切片不能用于逐请求长上下文判断。
- 用量扫描缓存和成本分析缓存都需更新，不能只修改最终费用计算函数。

## 3. 官方规则基线

按 2026-09-10 [Astra 官方模型页](https://developers.openai.com/api/docs/models/gpt-6-astra) 核对：基础输入、缓存读取、输出价格分别为每百万 Token 10、1、50 美元；缓存写入为 12.5 美元。请求输入严格超过 272,000 Token 时，输入和缓存价格乘 2，输出价格乘 1.5，作用于该请求整体。Fast 使用适用价格的 2 倍；Batch 和 Flex 为 Standard 的 50%。这些数值进入带来源的目录规则，不写死在通用计算函数中。

补充依据：[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[Fast mode](https://developers.openai.com/api/docs/guides/fast-mode)。API 文档的字段不能未经验证直接当作 Codex JSONL 的字段契约。

## 4. 用量数据和来源

为 UsageSlice 增加计价上下文，记录以下独立事实：

- 切片粒度：单次请求用量或累计回退。
- 缓存写入 Token：区分明确的 0 与未提供；不改变 totalTokens 的定义。
- 运行模式：standard、fast、flex、batch 或 unknown；同时记录来源是否为实际响应、请求设置或缺失。
- 请求标识或可验证的去重依据，仅在源数据提供时使用。

last_token_usage 的实际 input_tokens 用于单次请求阈值；累计回退不套用长上下文倍率。请求配置与实际服务等级分别表达，不能把请求意图描述为实际执行结果。当前样本缺少模式字段，第一轮实现不承诺自动识别 Fast；只有取得明确的 Codex 字段路径和语义证据后启用该适配器，其他情况为 unknown。

缓存写入字段出现时保留；确认其包含在 input_tokens 中后，将输入分成普通输入、缓存读取、缓存写入三部分，避免同时按普通输入和写入计费。字段缺失不填成已确认的 0；分区非法时保留原始 Token 总量并给出数据不足原因，不生成负数费用。API 的 cache_write_tokens 不与 JSONL 的 cache_write_input_tokens 混为同一个来源路径。

## 5. 价格目录与兼容

新增第二版目录 catalog-v2.json，包含基础价格、可选缓存写入单价、长上下文阈值与各类倍率、模式倍率和规则来源。仅允许声明式数值和已知枚举，禁止表达式或远程代码。

继续发布第一版 catalog.json 给已安装的一阶段客户端，避免格式升级导致旧客户端持续失败。发布器在同一个 pricing 分支提交中更新两份文件，并使用完整树保留两者。新版客户端优先读取第二版；第二版不存在时可明确回退第一版基础价格并显示规则不完整，不因网络异常覆盖有效的第二版缓存。

基础价和条件规则分别标注来源与核对日期。页面解析不明确时拒绝猜测规则；可维护经过官方来源核对的声明式规则文件。新增模型基础价格仍可自动同步，新计费维度需要明确适配。第一阶段官方源 403 尚未解决，真实采集和发布验证继续作为上线前检查，不在本阶段伪报通过。

## 6. 计算与缺失数据策略

逐请求先选择适用的长上下文规则，再对各输入分区和输出应用对应模式倍率，最后累加费用；先聚合后乘倍率会错算，禁止这样实现。reasoningOutputTokens 属于输出的明细，不另加一次费用。

采用以下产品口径：

1. 有明确基础价和所需条件：按匹配规则估算。
2. 有基础价但模式或条件不完整：继续提供参考金额，并标记为假设估算，列出缺失原因。模式缺失使用标准模式作为明确展示的假设；累计回退只做基础价估算，不把累计输入当作长请求。
3. 连基础价都没有：未计价，保留 Token，不按相近模型补价。

参考金额并不保证是上界或下界。对缺少缓存写入分区的旧记录保留基础输入估算，并标注未能应用完整缓存规则，不能把它说成完整费用。

建议新增通用计价质量信息，保留现有未知模型假设字段的语义，避免将模式缺失错误显示为未知模型补价。预算金额可继续包含明确标注的假设估算；告警同时展示估算依据。需要可靠费用覆盖的诊断和建议排除条件不完整切片，单独显示条件计价覆盖率。

## 7. 用户覆盖和界面

现有手动价格继续表示用户指定的平价假设，默认不叠加官方倍率，避免升级后改变用户已有假设。价格编辑器增加显式选项：使用目录条件规则；只有对应模型存在规则时可选，并预览影响。自定义模型缺少规则时保持平价估算。

模型价格页展示缓存写入单价、长上下文阈值、模式倍率及规则来源。费用汇总与会话详情展示规则匹配、包含假设、未计价状态，并给出可通过键盘访问的原因说明。中文和英文同步维护，不仅依赖颜色传递状态。

## 8. 缓存和全链路一致性

- 扫描缓存升级版本，旧缓存丢弃后只读重解析源日志；不能通过填默认 0 冒充获得缓存写入数据。
- 成本索引保留逐请求计价上下文；按模型或日期先汇总的旧桶不能继续作为条件计价输入。
- 成本缓存与价格签名纳入规则和条件上下文，变更后重建派生结果。
- 概览、预算、趋势、性能、诊断和情景分析统一调用条件计价入口；情景分析保留原始请求粒度，对缺少目标模型规则的条件明确降级。
- 价格更新沿用第一阶段的订阅和并发保护，不独立触发桌面预算通知。

## 9. 验收与测试

确认设计后按红—绿—重构实施，使用合成或脱敏 fixture 和独立临时目录；自动测试不读取真实会话目录。

- 阈值以下、等于 272,000、超过阈值，以及多个短请求累计超过阈值的区别。
- 缓存读取、写入、普通输入分区不重复计费；缺失、明确 0、非法值和语义未确认时的行为。
- Standard、Fast、Flex、Batch 和 unknown；不把请求配置当作实际执行等级。
- 累计回退、旧日志、模型切换和条件缺失，Token 总量保持一致。
- 手动平价覆盖与显式继承规则；未知模型仍未计价。
- v1/v2 目录同时发布、旧缓存重建、规则更新使派生价格失效。
- 所有费用入口一致，条件不完整状态正确传播，界面中文、英文和可访问性测试。
- npm test、npm run typecheck、npm run lint、npm run build 全部通过后才宣称本地实现验证通过；远程源验证单独报告。
